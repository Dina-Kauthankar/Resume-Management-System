1. PROJECT OVERVIEW & EXECUTIVE SUMMARY
================================================================================

1.1 Project Identification
- Formal Project Title: Resume Management & Smart Task Allocation System
- Package Identifier: resume (version 0.1.0)
- Enterprise Context: Demerge Systems India
- Architectural Paradigm: Unified Full-Stack Next.js Application (App Router architecture with Node.js Serverless Route Handlers, TypeScript Domain Layer, and Relational MySQL Persistence Layer)

1.2 Project Summary & Real-World Purpose
The recruitment and technical evaluation of human capital is one of the most resource-intensive bottlenecks faced by modern engineering enterprises. Traditional recruitment workflows rely heavily on manual document inspection, unstructured email exchanges, non-standardized evaluation criteria, and ad-hoc communication. This manual paradigm leads to critical inefficiencies:
1. Evaluation Fatigue & Subjectivity: HR managers reviewing hundreds of resumes face fatigue, leading to inconsistent evaluations, unconscious bias, and overlooked high-potential talent.
2. Inability to Process Heterogeneous Formats: Candidates submit resumes across diverse file extensions (PDF, Microsoft Word DOCX, LaTeX .tex source files) that require manual conversion or dedicated desktop software.
3. Lack of Quantitative Matching: Evaluating candidate compatibility against vacancy-specific technical requirements is typically qualitative rather than metric-driven.
4. The Batch Internship Allocation Problem: In academic and corporate internship programs where large cohorts of candidates are hired simultaneously, manual grouping into balanced engineering teams and assigning them to project sub-modules based on individual skill sets becomes mathematically intractable and prone to skill misalignments.

The "Resume Management & Smart Task Allocation System" was designed and implemented to provide a deterministic, transparent, and automated recruitment lifecycle. The system provides:
- Public discovery of active vacancies across distinct candidate categories (Single Job Seeker, Single Intern, Batch Intern).
- Secure, self-contained multi-format resume ingestion supporting PDF, DOCX, and LaTeX documents.
- In-memory server-side text extraction, sanitization, and Unicode normalization without reliance on external commercial SaaS APIs or Python sub-services.
- Transparent weighted keyword matching algorithms computing an absolute earned score and relative percentage confidence score.
- A deterministic two-stage heuristic allocation engine for batch internship programs that evaluates skill compatibility heatmaps across project modules and executes balanced snake round-robin team formation and skill-optimizing task assignment.
- An auditable application state machine preventing invalid state transitions and maintaining immutable historical logs of recruitment decisions.
- Synchronized interview appointment scheduling supporting both remote online sessions (with virtual meeting links) and in-person interviews (with physical location resolution).
- Persistent in-app database notifications, role-change request workflows, dynamic enterprise branding, and cryptographic password recovery with time-limited One-Time Passwords (OTPs).

2. PROBLEM STATEMENT
================================================================================

In contemporary software engineering and organizational talent acquisition, recruitment teams face multi-dimensional operational friction. Derived directly from the challenges addressed in the implemented codebase, the core problem statement comprises:

1. Heterogeneous Unstructured Ingestion:
Candidates submit curriculum vitae in varying formats. Standard screening pipelines fail when confronted with LaTeX documents (.tex), complex DOCX OpenXML structures, or multi-page PDF documents. The system must ingest, validate MIME types, enforce enterprise file-size thresholds, and extract clean, readable text strings directly in the server execution environment.

2. Absence of Objective, Deterministic Screening Metrics:
Human resume screening suffers from variance between evaluators. The system must establish a transparent evaluation algorithm where project creators assign specific numeric weights (signifying domain importance) to required technical competencies, and resumes are systematically analyzed against these weighted criteria to yield reproducible matching scores.

3. The Team Formation & Module Allocation Complexity in Batch Hiring:
When recruiting for collaborative internship batches, organizations receive hundreds of applications for complex software projects partitioned into distinct functional modules (e.g., Backend APIs, Frontend UI, Database Architecture, Machine Learning, DevOps). Selecting 20-50 candidates and manually assembling them into balanced, cross-functional squads while ensuring that every project module has a competent specialist is an NP-hard combinatorial problem. An automated, explainable, and deterministic allocation algorithm is required to resolve this without unpredictable artificial intelligence hallucinations.

4. Fragmented Communication & Appointment Scheduling:
Recruitment workflows frequently disconnect candidate status changes from interview logistics. A candidate shortlisted for an interview must be guaranteed valid state transitions (e.g., an applicant cannot be rejected while an interview is actively scheduled, nor can an interview be scheduled for an un-shortlisted candidate). Physical location details must be derived reliably from verified enterprise settings rather than ad-hoc text inputs.

5. Historical Integrity & Role Flexibility:
Candidates may register as individual job seekers but later wish to apply as batch interns or vice-versa. Updating a candidate's global profile must not retroactively corrupt the applicant type recorded on historical applications. A formal request-and-approval mechanism is required to maintain relational integrity and auditability.

3. PROJECT OBJECTIVES
================================================================================

3.1 Primary Objectives
- Automate the end-to-end recruitment process from public vacancy listing to application submission, resume parsing, candidate scoring, interview coordination, and final selection.
- Implement an automated, deterministic resume evaluation engine capable of parsing PDF, DOCX, and TeX files and computing weighted compatibility metrics against vacancy requirements.
- Develop a deterministic two-stage batch internship allocation algorithm that groups selected candidates into balanced squads and allocates functional project modules based on resume-demonstrated skill proficiencies.

3.2 Secondary Objectives
- Eliminate reliance on costly third-party AI APIs or fragile external microservices by implementing native TypeScript text extraction and matching logic.
- Provide a candidate experience with real-time application tracking, transparent score visualization, vacancy discovery, and team assignment dashboards.
- Provide an HR administrative command center featuring applicant tracking data tables, keyword management, module creation, candidate inspection popovers, and appointment scheduling.

3.3 Technical Objectives
- Enforce strict separation of concerns using a modular layered architecture: Presentation Layer (Next.js React Server & Client Components) -> API Routing Layer (Next.js Route Handlers) -> Domain Service Layer -> Data Access Repository Layer -> Relational Database Layer (MySQL).
- Guarantee zero data corruption through atomic database transactions (ACID compliance via MySQL InnoDB transactions) across multi-step mutations (e.g., simultaneous application submission and resume storage; atomic team creation and member allocation).
- Implement stateless, cryptographic authentication using JSON Web Tokens (JWT) signed with HMAC-SHA256 and transmitted exclusively via HTTP-only, secure, SameSite cookies.
- Maintain high security standards with salted bcrypt password hashing, input sanitization, parameterized SQL queries preventing SQL injection, and RFC-compliant validation schemas.

3.4 Recruitment & HR Objectives
- Empower HR managers to dynamically configure vacancy-specific keywords with customizable integer weights.
- Provide full control over recruitment policies, including allowed resume file formats, maximum upload size, company branding, and physical interview venues.
- Maintain an immutable audit log (`application_status_history`) recording every recruitment state transition along with evaluator identity and textual decision notes.

3.5 Candidate & User Objectives
- Enable streamlined application workflows with instant client-side file validation and feedback.
- Provide an application tracking interface displaying application status, match percentage, earned score, and interview appointments.
- Allow candidates to request job role / applicant type changes with automated notifications upon HR approval or rejection.
- Deliver an interactive Team Dashboard for batch interns detailing assigned project modules, team name, and assigned teammates with their respective module responsibilities.

4. TECHNOLOGY STACK SPECIFICATION
================================================================================

The system is constructed entirely on an enterprise-grade TypeScript/JavaScript modern web architecture. All components and packages have been verified from `package.json` and imports in active source files.

4.1 Frontend Technologies
- Framework: Next.js (Version 16.3.6) utilizing the modern App Router architecture (`app/` directory). Employs React Server Components (RSC) for initial page renders and React Client Components (`"use client"`) for rich interactive forms, modals, tables, and dropdowns.
- Core UI Library: React (Version 19.2.8) and React DOM (Version 19.2.8).
- Language: TypeScript (Version 5) providing end-to-end static type safety across components, props, DTOs, and API responses.
- Styling & CSS Architecture: Tailwind CSS (Version 4) coupled with `@tailwindcss/postcss`. Uses utility-first CSS, modern CSS grid and flexbox, custom color palettes, and responsive breakpoints (`sm`, `md`, `lg`, `xl`).
- Headless Data Table: `@tanstack/react-table` (Version 9.2.4) powering the HR application management data table with multi-column sorting, pagination, filtering, and custom cell renderers.
- Toast & UI Notification System: `sonner` (Version 2.0.8) providing accessible, non-blocking toast notifications for client feedback.
- Icons & Media: Native inline SVG icons integrated directly into navigation shells and status badges, eliminating external heavy icon font bundles.

4.2 Backend & Server-Side Technologies
- Server Environment: Node.js (Node runtime explicitly specified via `export const runtime = "nodejs"` in route handlers requiring filesystem access, Buffer operations, and crypto primitives).
- Routing Architecture: Next.js App Router API Routes (`route.ts`) implementing RESTful HTTP methods (GET, POST, PUT, DELETE).
- Authentication & Cryptography:
  * `jose` (Version 6.2.12): Modern, zero-dependency JOSE implementation utilized for signing and verifying JSON Web Tokens (JWT) using HMAC-SHA256 (HS256).
  * `bcryptjs` (Version 3.0.3): Optimized JavaScript implementation of the bcrypt password-hashing function using salt generation (10 rounds).
  * Native Node.js `crypto`: Utilized for generating cryptographically secure pseudo-random numbers (CSPRNG) for 6-digit password reset OTPs (`crypto.randomInt`) and 32-byte hex reset authorization tokens (`crypto.randomBytes`), as well as SHA-256 hash generation for OTP storage.
- Mail Transport: `nodemailer` (Version 10.0.10) with `@types/nodemailer` (Version 8.0.2) supporting authenticated SMTP email delivery with graceful development fallback logging.
- Document Processing & Extraction Libraries:
  * `pdf-parse` (Version 2.4.5) with `pdf-parse/worker`: Server-side extraction of text layers from binary PDF buffers.
  * `mammoth` (Version 1.12.3): Specialized library for converting Microsoft Word .docx OpenXML documents into raw plaintext by inspecting document paragraphs and runs.
  * Native Node.js `Buffer`: Decoding LaTeX .tex UTF-8 plaintext source files directly from memory buffers.

4.3 Database & Persistence Layer
- Database Engine: MySQL Relational Database Management System (RDBMS) configured with InnoDB storage engine for full ACID transaction support and foreign key enforcement.
- Database Driver: `mysql2` (Version 3.24.4) utilizing `mysql2/promise` for asynchronous, promise-based connection pool management.
- Connection Management: Centralized connection pool (`server/database/connection.ts`) utilizing `createPool` with a maximum limit of 10 concurrent connections, connection waiting queues, and a global caching mechanism during development (`globalThis.mysqlPool`) to prevent pool exhaustion across Next.js Hot Module Replacement (HMR) reloads.
- Schema Definition: Pure SQL schema definition (`server/database/database.sql`) comprising 15 normalized tables, foreign key constraints with cascading deletions/updates, unique constraints, and optimized secondary B-tree indexes.

4.4 Development & Tooling
- Package Manager: npm (configured with lockfile version 3).
- Linter: ESLint (Version 9) configured via `eslint.config.mjs` extending `eslint-config-next` (Version 16.3.6).
- TypeScript Compiler: `tsc` with `tsconfig.json` enforcing strict null checks, ES2017 target, module resolution via bundler, and path alias mapping `@/*` pointing to project root.

5. SYSTEM ARCHITECTURE
================================================================================

The application adheres strictly to a clean, multi-tier architectural pattern. The layers and their designated responsibilities are structured as follows:

                        +---------------------------------------+
                        |           USER INTERFACE              |
                        |   Browser (Desktop, Tablet, Mobile)   |
                        +---------------------------------------+
                                           |
                                      HTTP / HTTPS
                                           |
                        +---------------------------------------+
                        |        NEXT.JS APP ROUTER             |
                        | Pages, Layouts, Server Components     |
                        | (app/(client)/page.tsx, hr/, cand/)   |
                        +---------------------------------------+
                                           |
                                  Internal Fetch / RPC
                                           |
                        +---------------------------------------+
                        |        API ROUTING LAYER              |
                        | Next.js Route Handlers (app/api/**)   |
                        | Authentication & DTO Validation Check |
                        +---------------------------------------+
                                           |
                                     Function Calls
                                           |
                        +---------------------------------------+
                        |          SERVICE LAYER                |
                        | Business Logic, Extraction, Matching, |
                        | Batch Allocation (server/services/**) |
                        +---------------------------------------+
                                           |
                                     Function Calls
                                           |
                        +---------------------------------------+
                        |       REPOSITORY LAYER (DAO)          |
                        | SQL Query Construction, Data Mapping  |
                        | (server/repositories/**)              |
                        +---------------------------------------+
                                           |
                                Connection Pool Queries
                                           |
                        +---------------------------------------+
                        |        DATABASE LAYER (MySQL)         |
                        | InnoDB Tables, Constraints, Indexes   |
                        | (resume_db / 15 Relational Tables)    |
                        +---------------------------------------+

5.1 Architectural Layer Responsibilities
1. User Interface (Presentation) Layer:
   - Formulates interactive views using React 19 Client Components.
   - Manages local UI states (e.g., modal visibility, loading spinners, form inputs).
   - Renders data tables, badges, filter pills, and score breakdowns.
   - Communicates with the backend exclusively via asynchronous HTTP `fetch` calls to `/api/**`.

2. Next.js Edge / Middleware Layer (`middleware.ts`):
   - Intercepts inbound HTTP requests before they reach page components or route handlers.
   - Validates the `auth_token` HTTP cookie using `jose` JWT verification.
   - Enforces Role-Based Access Control (RBAC):
     * Non-authenticated users accessing `/hr/**` or `/candidate/**` are redirected to `/login` with an appended `callbackUrl`.
     * Authenticated candidates attempting to access `/hr/**` are redirected to `/candidate/dashboard`.
     * Authenticated HR users attempting to access `/candidate/**` are redirected to `/hr/dashboard`.
     * Authenticated users visiting `/login` or `/register` are redirected to their respective dashboards.

3. API Route Handler Layer (`app/api/**`):
   - Serves as the HTTP boundary.
   - Extracts URL parameters, query strings, multipart form data, and JSON bodies.
   - Validates session permissions using `getAuthSession()`.
   - Delegates business computation to the domain service layer.
   - Maps domain exceptions and errors to standard HTTP status codes (200, 201, 400, 401, 403, 404, 409, 422, 500).

4. Domain Service Layer (`server/services/**`):
   - Encapsulates enterprise business logic and domain invariants.
   - Houses the deterministic keyword matching algorithms (`calculateKeywordMatch`).
   - Houses document extraction dispatching (`extractResumeText`).
   - Implements the two-stage heuristic batch internship allocation algorithm (`generateAllocationDraft`).
   - Manages state transition verification (e.g., verifying an interview is not scheduled before rejecting).
   - Coordinates transactional notification dispatching across candidates and HR.

5. Repository / Data Access Layer (`server/repositories/**`):
   - Isolates all direct SQL query syntax and relational mapping logic.
   - Executes parameterized queries via `db.execute()` and `db.query()` to eliminate SQL injection vulnerabilities.
   - Handles low-level database connection acquisitions and transaction lifecycles (`connection.beginTransaction()`, `connection.commit()`, `connection.rollback()`, `connection.release()`).
   - Maps raw MySQL `RowDataPacket` arrays into typed TypeScript interfaces.

6. Database Layer (`server/database/database.sql`):
   - MySQL 8.x running with InnoDB engine.
   - Stores persistent relational data across 15 normalized tables.
   - Guarantees referential integrity through foreign key cascades and checks.

  * Schedule, reschedule, update, and complete online or offline interview appointments.
  * Execute the automated Two-Stage Batch Allocation Heuristic Engine to generate team recommendations.
  * Manually override, adjust, and transactionally confirm batch intern team allocations.
  * Review, approve, or reject candidate job role change requests.
  * Configure enterprise settings: company branding, allowed resume file formats, maximum file size, and notification preferences.
- Access Restrictions:
  * Cannot submit applications or apply to vacancies.
  * Guided by the middleware away from candidate portal views (`/candidate/**`).

8. AUTHENTICATION, SESSION MANAGEMENT & AUTHORIZATION FRAMEWORK
================================================================================

8.1 Authentication Architecture
The system implements a stateless, token-based authentication mechanism utilizing JSON Web Tokens (JWT) and cryptographically secure password hashing.

- Password Storage Security:
  * Handled via `bcryptjs`.
  * Passwords are never stored in plaintext.
  * Upon registration or password reset, passwords are processed through `bcrypt.genSalt(10)` and hashed using the bcrypt adaptive hashing function before insertion into the `users` table.
  * During login, credentials are verified using constant-time password comparison `bcrypt.compare(password, user.password)`.

- Token Generation & Specification:
  * Implemented using `jose` (`SignJWT` and `jwtVerify`).
  * Algorithm: HMAC using SHA-256 (`HS256`).
  * Signing Key: Derived from `process.env.JWT_SECRET` (falling back to a default secret in non-production environments).
  * Token Lifetime: Exactly 24 hours (`.setExpirationTime("24h")`).
  * JWT Payload Structure:
    {
      "userId": 14,
      "email": "candidate@example.com",
      "fullName": "Jane Doe",
      "role": "CANDIDATE",
      "applicantType": "BATCH_INTERN",
      "iat": 1774800000,
      "exp": 1774886400
    }

- Cookie Storage Strategy:
  * Tokens are dispatched to the browser within an HTTP cookie named `auth_token`.
  * Cookie Parameters:
    - `httpOnly: true` (Prevents client-side JavaScript access via `document.cookie`, mitigating Cross-Site Scripting [XSS] token theft).
    - `secure: process.env.NODE_ENV === "production"` (Ensures transmission exclusively over TLS/HTTPS in production).
    - `sameSite: "lax"` (Mitigates Cross-Site Request Forgery [CSRF] while allowing standard top-level navigation).
    - `path: "/"` (Available across all application routes).
    - `maxAge: 86400` (24 hours in seconds).

8.2 Session Verification & Route Protection
Authentication is enforced at two distinct defensive perimeters:

Perimeter 1: Next.js Edge Middleware (`middleware.ts`)
The middleware intercepts all requests matching `/hr/:path*`, `/candidate/:path*`, `/login`, and `/register`.
- Extracts `auth_token` from incoming cookies.
- Verifies the cryptographic signature and expiration of the token using `jwtVerify`.
- If valid, inspects the `role` attribute:
  * Requests to `/hr/**` require `role === "HR"`. If unauthenticated, redirects to `/login?callbackUrl=/hr/...`. If authenticated as `CANDIDATE`, redirects to `/candidate/dashboard`.
  * Requests to `/candidate/**` require `role === "CANDIDATE"`. If unauthenticated, redirects to `/login?callbackUrl=/candidate/...`. If authenticated as `HR`, redirects to `/hr/dashboard`.
  * Requests to `/login` or `/register` when already authenticated redirect immediately to the respective role dashboard.

Perimeter 2: Server-Side API Handlers (`getAuthSession()`)
Every protected API route handler calls `await getAuthSession()`, which accesses the Next.js `cookies()` store on the server, verifies the JWT, and validates payload integrity:
- Checks that `userId` is a valid number, `email` and `fullName` are strings, and `role` and `applicantType` match strict database ENUM values.
- If validation fails, the API immediately terminates and returns `401 Unauthorized`.
- Handlers perform secondary role checks (e.g., `if (session.role !== "HR") return NextResponse.json({ error: "Forbidden" }, { status: 403 })`).

8.3 Cryptographic Password Recovery (Forgot Password Workflow)
Password recovery is implemented via an out-of-band email verification workflow without transmitting permanent authentication credentials. The process comprises three distinct phases:

Phase 1: OTP Request (`POST /api/auth/forgot-password/request-otp`)
1. User provides their account email address.
2. The system checks `users` table via `userRepository.findUserByEmail()`.
3. To prevent email enumeration attacks, the API returns a generic success response (`"If an account exists for this email, an OTP has been sent."`) regardless of whether the user exists.
4. If the user exists:
   - Generates a 6-digit numeric OTP using `crypto.randomInt(100000, 1000000)`.
   - Hashes the OTP using SHA-256 (`crypto.createHash("sha256").update(otp).digest("hex")`).
   - Inserts a record into `password_reset_tokens` with `user_id`, `otp_hash`, `expires_at = NOW() + 5 minutes`, and `attempts = 0`.
   - Dispatches a formatted HTML email containing the plaintext OTP via Nodemailer (`emailService.sendPasswordResetOTPEmail`).

Phase 2: OTP Verification (`POST /api/auth/forgot-password/verify-otp`)
1. User submits their email address and the 6-digit OTP.
2. System retrieves the latest unexpired, unused token record for the user.
3. Brute-Force Rate Limiting: The system enforces a maximum threshold of 5 failed attempts (`activeToken.attempts >= 5`). If exceeded, the token is permanently invalidated (`is_used = 1`) and rejected.
4. The submitted OTP is hashed with SHA-256 and compared against `otp_hash`.
5. If invalid, `attempts` is incremented by 1, and the remaining attempt count is returned.
6. If valid:
   - Generates a cryptographically strong 32-byte temporary reset authorization token (`crypto.randomBytes(32).toString("hex")`).
   - Hashes this token with SHA-256 and updates `password_reset_tokens.reset_token_hash`.
   - Returns the plaintext reset token to the client.

Phase 3: Password Update (`POST /api/auth/forgot-password/reset-password`)
1. User submits the reset authorization token, new password, and password confirmation.
2. System validates that the password is at least 6 characters and matches confirmation.
3. Hashes the incoming reset token with SHA-256 and queries `password_reset_tokens` for an active, unused token matching `reset_token_hash`.
4. If found:
   - Hashes the new password using `hashPassword` (bcrypt with 10 salt rounds).
   - Updates `users.password` where `id = tokenRecord.user_id`.
   - Immediately consumes the token (`is_used = 1`).
   - Returns success, allowing the candidate to log in with their updated credentials.

11.2 Storage Structure & Characterization
- Filesystem Storage Path:
  `process.cwd() + "/uploads/resumes/user-" + candidate.id + "/" + safeFileName`
- Sanitized Filename Pattern:
  `${Date.now()}-${resume.name.replace(/[^a-zA-Z0-9._-]/g, "_")}`
- Database Storage:
  The `resumes` table stores metadata (`file_name`, `file_extension`, `file_path`, `character_count`, `word_count`, `uploaded_at`) alongside the complete sanitized text in a `longtext` column (`extracted_text`).
- Fault Tolerance & Cleanup:
  If the database transaction encounters an error after the resume file has been written to the disk, the catch block calls `await fs.unlink(savedFilePath)` to eliminate orphaned files before rolling back the transaction.

12. DOCUMENT TEXT EXTRACTION ENGINE (PDF, DOCX, LATEX)
================================================================================

The extraction subsystem is implemented entirely in TypeScript within `server/extraction/` and executes within the Node.js runtime without external microservices.

12.1 Supported Document Formats
1. Portable Document Format (.pdf):
   - Library: `pdf-parse` (v2.4.5) utilizing `pdf-parse/worker`.
   - Implementation: In `server/extraction/pdfExtractor.ts`, initializes `PDFParse` with `PDFParse.setWorker(getPath())`.
   - Operation: Ingests the binary buffer, extracts embedded text layers across all document pages, and guarantees resource cleanup in a `finally` block via `parser.destroy()`.
2. Microsoft Word OpenXML (.docx):
   - Library: `mammoth` (v1.12.3).
   - Implementation: In `server/extraction/docxExtractor.ts`, invokes `mammoth.extractRawText({ buffer: fileBuffer })`.
   - Operation: Parses the zipped XML document structure, extracting text runs while ignoring proprietary styling tags.
3. LaTeX Source File (.tex):
   - Implementation: In `server/extraction/texExtractor.ts`, decodes the buffer as UTF-8 plaintext using `fileBuffer.toString("utf8")`.
   - Operation: Processes raw academic and scientific resumes authored in LaTeX.

12.2 Text Cleaning & Normalization Pipeline (`cleaner.ts`)
Raw extracted text is passed through `cleanExtractedText(rawText)` to ensure high-fidelity keyword matching:
1. LaTeX Command Stripping:
   - Command with arguments: `/\\(?:textbf|textit|emph|underline|section|subsection|subsubsection|caption|title|author|href)\{([^}]*)\}/g` replaces commands with inner text contents.
   - Command identifiers: `/\\[a-zA-Z]+/g` stripped to single spaces.
   - Comments: `/%.*$/gm` stripped completely.
   - Environments: `/\\(?:begin|end)\{[^}]*\}/g` stripped.
2. Unicode Normalization:
   - Text is normalized to Canonical Decomposition followed by Canonical Composition (`text.normalize("NFC")`).
   - Non-breaking spaces (`\u00a0`) and horizontal tabs (`\t`) converted to standard ASCII spaces.
3. Ligature & Hyphen Harmonization:
   - Replaces typographic ligatures: `ﬁ` -> `fi`, `ﬂ` -> `fl`.
   - Replaces em-dashes and en-dashes: `–` and `—` -> standard hyphen `-`.
4. Control Character Removal:
   - Strips unprintable control characters: `/[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]/g`.
5. Whitespace Collapsing:
   - Splits lines by `\r?\n`, trims each line, collapses internal multiple spaces to a single space, and filters out empty lines.

12.3 Extraction Edge Cases & Scanned Document Handling
- Empty / Scanned PDF Detection:
  Optical Character Recognition (OCR) is not integrated into the current codebase. If a candidate uploads a scanned image wrapped in a PDF or an empty document, the cleaned text length will be below 15 characters.
- In `extractor.ts`:
  ```typescript
  if (cleanedText.trim().length < 15) {
    throw new Error(
      "The uploaded document contains no readable text. It may be a scanned image-based PDF or an empty document."
    );
  }
  ```
  This immediately aborts application submission with HTTP status `422 Unprocessable Entity`, preventing blank or unscorable resumes from entering the database.

13. WEIGHTED KEYWORD MATCHING & CONFIDENCE SCORING ALGORITHMS
================================================================================

The evaluation subsystem (`server/matching/keywordMatcher.ts`) performs objective, quantitative scoring of candidate resumes against vacancy requirements.

13.1 Mathematical Specification & Formal Formulae
Let:
- $R$ be the normalized resume text string.
- $K = \{k_1, k_2, \dots, k_n\}$ be the set of configured project keywords.
- $w_i \in \mathbb{N}_{\ge 1}$ be the positive integer weight assigned to keyword $k_i$.
- $\text{norm}(s)$ be the string normalization function: $\text{norm}(s) = \text{trim}(\text{lowercase}(\text{collapse\_spaces}(s)))$.

The binary match indicator $m_i$ for keyword $k_i$ is defined as:
$$m_i = \begin{cases} 1 & \text{if } \text{norm}(k_i) \subseteq \text{norm}(R) \\ 0 & \text{otherwise} \end{cases}$$

1. Earned Absolute Score ($S$):
$$S = \sum_{i=1}^{n} (m_i \times w_i)$$

2. Maximum Possible Score ($S_{\max}$):
$$S_{\max} = \sum_{i=1}^{n} w_i$$

3. Percentage Confidence Score ($C$):
$$C = \begin{cases} 0.00 & \text{if } S_{\max} = 0 \\ \text{round}\left( \frac{S}{S_{\max}} \times 100, 2 \right) & \text{if } S_{\max} > 0 \end{cases}$$

13.2 Partitioning of Matched vs. Missing Keywords
During evaluation, keywords are partitioned into two distinct sets:
$$K_{\text{matched}} = \{k_i \in K \mid m_i = 1\}$$
$$K_{\text{missing}} = \{k_i \in K \mid m_i = 0\}$$
The count of matched keywords stored in `applications.matched_keywords` is simply $|K_{\text{matched}}|$.

13.3 Worked Conceptual Example
Consider a Vacancy titled "Full Stack Engineer" configured with 5 project keywords:
1. "Next.js" (Weight = 10)
2. "TypeScript" (Weight = 9)
3. "React" (Weight = 8)
4. "MySQL" (Weight = 7)
5. "Docker" (Weight = 6)

Maximum Possible Score:
$$S_{\max} = 10 + 9 + 8 + 7 + 6 = 40$$

Candidate Resume Text:
"Experienced developer skilled in building web applications with React, TypeScript, and MySQL databases."

Evaluation Execution:
- "next.js" in text? -> NO  ($m_1 = 0$, score contribution = 0)
- "typescript" in text? -> YES ($m_2 = 1$, score contribution = 9)
- "react" in text? -> YES ($m_3 = 1$, score contribution = 8)
- "mysql" in text? -> YES ($m_4 = 1$, score contribution = 7)
- "docker" in text? -> NO  ($m_5 = 0$, score contribution = 0)

Computed Outputs:
- $S = 0 + 9 + 8 + 7 + 0 = 24$
- $|K_{\text{matched}}| = 3$ (React, TypeScript, MySQL)
- $|K_{\text{missing}}| = 2$ (Next.js, Docker)
- $C = \text{round}\left( \frac{24}{40} \times 100, 2 \right) = 60.00\%$

Resulting Record Stored in `applications`:
- `score` = 24
- `matched_keywords` = 3
- `confidence_percentage` = 60.00

14. BATCH INTERNSHIP SYSTEM & TWO-STAGE HEURISTIC ALLOCATION ALGORITHM
================================================================================

The Batch Internship Allocation engine (`server/services/batchAllocationService.ts` and `server/repositories/batchAllocationRepository.ts`) solves the problem of organizing selected batch candidates into collaborative teams and assigning them functional project modules.

14.1 Candidate Eligibility Invariant
The allocation engine strictly enforces that only candidates meeting all three of the following relational conditions are eligible:
1. `applications.project_id = target_project_id`
2. `applications.applicant_type = 'BATCH_INTERN'`
3. `applications.status = 'SELECTED'`
Candidates with statuses `APPLIED`, `SHORTLISTED`, `INTERVIEW_SCHEDULED`, or `REJECTED` are strictly excluded from team formation.

14.2 Candidate-Module Skill Compatibility Formula
Each project module $m \in M$ specifies a comma- or semicolon-separated string of required skills $K_m = \{s_1, s_2, \dots, s_p\}$ parsed via `parseModuleSkills()`.
If $K_m = \emptyset$, compatibility is defined as 100%.
Otherwise, for candidate resume text $R_c$, the match indicator for skill $s \in K_m$ is:
$$\text{match}(c, s) = \begin{cases} 1 & \text{if } \text{norm}(s) \subseteq \text{norm}(R_c) \\ 0 & \text{otherwise} \end{cases}$$

The Compatibility Percentage $C(c, m)$ of candidate $c$ for module $m$ is:
$$C(c, m) = \text{round}\left( \frac{\sum_{s \in K_m} \text{match}(c, s)}{|K_m|} \times 100 \right)$$

14.3 The Two-Stage Deterministic Allocation Algorithm
The allocation engine is completely deterministic, explainable, and reproducible without relying on non-deterministic generative LLMs.

Target Team Sizing:
Let $N$ be the number of eligible candidates, and $T_{\text{target}}$ be the target squad size (default = 4, bounded between 2 and 10).
The number of teams $K_{\text{teams}}$ is calculated as:
$$K_{\text{teams}} = \max\left(1, \text{round}\left(\frac{N}{T_{\text{target}}}\right)\right)$$
If $K_{\text{teams}} > 1$ and $N / K_{\text{teams}} < 2$, $K_{\text{teams}}$ is adjusted to $\max(1, \lfloor N / 2 \rfloor)$.

Stage 1: Team Formation (Skill Diversity & Balanced Capacity)
1. For every candidate, identify their Primary Module: the module $m^*$ yielding the highest compatibility score $\max_m C(c, m)$.
2. Group candidates by their primary module: $G_m = \{c \mid m^* = m\}$.
3. Sort candidates within each module group in descending order of their compatibility score.
4. Distribute candidates across the $K_{\text{teams}}$ teams using a balanced snake round-robin method:
   - Candidates are assigned to the team with the smallest current membership.
   - Ties are broken using an oscillating snake pointer (Team $1 \to K$, then Team $K \to 1$).
   - This ensures every team receives top talent and diverse primary skill sets while maintaining equal squad sizes.

Stage 2: Module Assignment Within Teams (Skill Optimization & Coverage)
For each team formed in Stage 1:
1. Sort all project modules in descending order of the team's average compatibility for that module.
2. Distinct Module Assignment: For each sorted module, assign the best unassigned team member who has the highest compatibility score for that module.
3. Surplus Candidate Assignment: If squad size exceeds the count of project modules, remaining unassigned members are assigned to their personal highest-scoring module.
4. Warning Generation:
   - If an assigned candidate's compatibility is below 60%, generate a `LOW_COMPATIBILITY` warning.
   - If a project module has no team member assigned to it, generate an `UNCOVERED_MODULE` warning.
   - Calculate Team Average Compatibility as the arithmetic mean of all member compatibilities.

14.4 Confirmation & Atomic Persistence
When HR reviews the draft allocation and confirms:
1. Input Payload Validation (`validateConfirmedTeamsPayload`): Verifies non-empty arrays, positive integers for IDs, and ensures no candidate or application is duplicated across squads.
2. Transactional Database Execution:
   - Acquires database connection and begins transaction.
   - Re-verifies all applications are `SELECTED`, `BATCH_INTERN`, and belong to the project.
   - Atomically deletes any previously confirmed teams and memberships for this project (`DELETE FROM team_members`, `DELETE FROM teams`).
   - Inserts new records into `teams` (e.g., "Team Alpha", "Team Beta").
   - Inserts records into `team_members` with `team_id`, `user_id`, `application_id`, and `project_module_id`.
   - Generates in-app notifications (`BATCH_TEAM_ASSIGNED`) for every assigned candidate.
   - Commits transaction.

16. RECRUITMENT APPLICATION LIFECYCLE & STATE MACHINE
================================================================================

16.1 Application Status State Machine
An application progresses through a well-defined set of states represented by the ENUM in `applications.status`:

                     +-----------------+
                     |     APPLIED     | <--- (Initial state upon submission)
                     +-----------------+
                              |
                              v
                     +-----------------+
                     |   SHORTLISTED   |
                     +-----------------+
                        |           |
                        |           v
                        |     +-----------------------+
                        |     |  INTERVIEW_SCHEDULED  |
                        |     +-----------------------+
                        |           |
                        +-----+-----+
                              |
               +--------------+--------------+
               |                             |
               v                             v
      +-----------------+           +-----------------+
      |    SELECTED     |           |    REJECTED     |
      | (Terminal State)|           | (Terminal State)|
      +-----------------+           +-----------------+

16.2 State Transition Invariants & Guard Rules
Implemented in `app/api/hr/application/[applicationId]/route.ts`:
1. Terminal Decisions Immutability:
   Once an application transitions to `SELECTED` or `REJECTED`, its state is permanently frozen. Any attempt to update status returns `400 Bad Request` (`"Application is in terminal state (${oldStatus}) and cannot be changed."`).
2. Interview Module Exclusivity:
   HR cannot change an application's status to `INTERVIEW_SCHEDULED` via the standard application PUT endpoint. Transition to `INTERVIEW_SCHEDULED` can only occur by scheduling an interview through the interview module (`scheduleInterview()`).
3. Scheduled Interview Invariant:
   If an application is in `INTERVIEW_SCHEDULED` status and an interview appointment exists with status `SCHEDULED`, HR is forbidden from selecting or rejecting the candidate until the interview appointment has been marked `COMPLETED` or `CANCELLED`.
4. Shortlisting Requirement for Interviews:
   An interview can only be scheduled for an application whose status is `SHORTLISTED` (or already `INTERVIEW_SCHEDULED` when updating).

16.3 Decision Audit Logging (`application_status_history`)
Every valid status transition executes within a MySQL transaction that inserts a record into `application_status_history`:
- `application_id`: Target application.
- `old_status`: Previous status string.
- `new_status`: Updated status string.
- `changed_by`: User ID of the HR evaluator.
- `decision_note`: Optional or mandatory textual rationale entered by HR.
- `changed_at`: Timestamp of the decision.

17. INTERVIEW SCHEDULING & APPOINTMENT MANAGEMENT SYSTEM
================================================================================

17.1 Appointment Architecture
Interview logistics are decoupled from the application entity and persisted in the dedicated `appointments` table.

- Appointments Table Structure:
  * `id` INT AUTO_INCREMENT PRIMARY KEY
  * `application_id` INT NOT NULL (FK -> `applications.id` ON DELETE CASCADE)
  * `interview_date` DATE NOT NULL
  * `interview_time` TIME NOT NULL
  * `meeting_link` VARCHAR(500) NULL (Required for ONLINE)
  * `physical_location` VARCHAR(500) NULL (Required for OFFLINE)
  * `interview_type` ENUM('ONLINE', 'OFFLINE') DEFAULT 'ONLINE'
  * `status` ENUM('SCHEDULED', 'COMPLETED', 'CANCELLED') DEFAULT 'SCHEDULED'
  * `notes` TEXT NULL
  * `created_by` INT NULL (FK -> `users.id` ON DELETE SET NULL)
  * `created_at`, `updated_at` DATETIME(3)

17.2 Interview Scheduling Workflow (`scheduleInterview`)
1. Application Verification: Retrieves application; validates status is `SHORTLISTED` or `INTERVIEW_SCHEDULED`.
2. Date & Time Validation:
   - `isValidDate`: Regex `/^\d{4}-\d{2}-\d{2}$/` and calendar date validity check.
   - `isValidTime`: Regex `/^\d{2}:\d{2}(:\d{2})?$/`.
3. Location / Link Resolution:
   - For `ONLINE`: `meetingLink` is required; `physicalLocation` is set to null.
   - For `OFFLINE`: `meetingLink` is set to null. Physical location is resolved via strict priority:
     * Priority 1: Explicit interview-specific location entered by HR in the form.
     * Priority 2: Fallback to `company_settings.address`. If neither exists, throws `400 Bad Request`. (Note: The application intentionally does not use `users.company_address`).
4. Idempotent Appointment Creation:
   - If an interview appointment already exists for this application, the record is updated rather than creating duplicates.
   - If no interview exists, inserts into `appointments` and updates `applications.status = 'INTERVIEW_SCHEDULED'` within a single transaction.
5. Notification Dispatch:
   - Sends in-app notification to candidate detailing date, time, mode, and link/venue.
   - Sends confirmation in-app notification to HR.

17.3 Interview Modification & Completion (`modifyInterview`)
HR can update interview date, time, notes, or change appointment status:
- `SCHEDULED`: Interview is pending.
- `COMPLETED`: Interview took place. Unlocks the application, allowing HR to make final `SELECTED` or `REJECTED` decisions.
- `CANCELLED`: Interview was called off.

18. MULTI-CHANNEL NOTIFICATION SUBSYSTEM & PREFERENCES

18.1 In-App Database Notifications (`notifications` Table)
The system maintains a persistent, relational notification pipeline. In-app notifications are stored in the `notifications` table:

- Read State Management:

  * Clicking an item calls `PATCH /api/notifications/[id]/read`.

18.2 Notification Types & Event Triggers
- Candidate Notifications:
  * `APPLICATION_SHORTLISTED`: Fired when application status becomes SHORTLISTED.
  * `APPLICATION_SELECTED`: Fired when application status becomes SELECTED.
  * `APPLICATION_REJECTED`: Fired when application status becomes REJECTED.
  * `INTERVIEW_SCHEDULED`: Fired when HR schedules an interview appointment.
  * `INTERVIEW_UPDATED` / `INTERVIEW_CANCELLED`: Fired when interview details or status change.
  * `BATCH_TEAM_ASSIGNED`: Fired when HR confirms batch intern squad allocations.
  * `JOB_ROLE_APPROVED` / `JOB_ROLE_REJECTED`: Fired when HR acts on role change requests.

  * `NEW_APPLICATION`: Dispatched when a candidate applies (subject to HR preferences).
  * `INTERVIEW_SCHEDULED` / `INTERVIEW_CANCELLED`: Dispatched upon interview actions.
  * `APPLICATION_SELECTED`: Dispatched when an applicant is selected.
  * `JOB_ROLE_REQUEST`: Dispatched when a candidate requests an applicant type change.

- `notify_interviews` (Default = 1)
- `notify_selections` (Default = 1)
- `notify_batch_allocations` (Default = 1)
Dispatches verify these flags via `getUserNotificationPreferences(hrUserId)` prior to insertion.

18.4 Email Notification Scope (Distinction from In-App)
- Actual Implemented Email Scope:
  Email delivery via Nodemailer is implemented strictly for Password Reset OTP delivery (`emailService.sendPasswordResetOTPEmail`).
- General Notifications:
  Routine application status changes, interview announcements, and team allocations are delivered via in-app database notifications and UI toasts, NOT via email.

22. END-TO-END DATA FLOW
================================================================================

22.1 Candidate Registration & Application Submission Flow
1. Candidate completes registration on `/register` -> `POST /api/auth/register`.
2. Backend validates data, hashes password with bcrypt, inserts into `users`, generates JWT, sets HTTP-only `auth_token` cookie, returns user session.
3. Candidate navigates to `/candidate/projects`, selecting a project matching their applicant type.
4. On `/candidate/projects/[id]/apply`, candidate uploads resume file and clicks Submit.
5. Form issues `POST /api/applications` with multipart form data.
6. Server checks JWT cookie, verifies file against `company_settings`, and converts ArrayBuffer to Node.js Buffer.
7. Dispatches to `extractResumeText(buffer, extension)`, stripping LaTeX/formatting and returning cleaned text.
8. Verifies text >= 15 characters.
9. Executes `calculateKeywordMatch(cleanedText, projectKeywords)`: calculates earned score, matched keywords, and confidence percentage.
10. Saves original document to `uploads/resumes/user-[id]/`.
11. In a single MySQL transaction, inserts into `applications` and `resumes`.
12. Dispatches in-app notification to HR (`NEW_APPLICATION`).
13. Returns JSON response containing score, confidence %, and matched/missing keyword arrays.

22.2 HR Application Review & Status Transition Flow
1. HR navigates to `/hr/application` -> fetches applications via `GET /api/hr/application`.
2. Server loads applications, joins project keywords, executes live keyword enrichment, and returns candidate data.
3. HR clicks on an applicant -> loads `/hr/application/[applicationId]`.
4. HR inspects keyword breakdown, scores, and optionally clicks Download Resume (`GET /api/hr/application/[id]/resume?download=true`).
5. HR selects "SHORTLISTED" with note "Strong React fundamentals" -> `PUT /api/hr/application/[applicationId]`.
6. Server checks RBAC, validates status transition, starts transaction, updates `applications.status`, inserts audit log into `application_status_history`, and commits.
7. Server dispatches `APPLICATION_SHORTLISTED` in-app notification to candidate.

22.3 Interview Scheduling Flow
1. For a shortlisted candidate, HR opens `/hr/interview/[applicationId]` -> `POST /api/hr/interview/[applicationId]`.
2. Form submits date, time, mode (`ONLINE` vs `OFFLINE`), meeting link, and notes.
3. Server executes `scheduleInterview()`:
   - Validates date and time format.
   - For `OFFLINE`, resolves venue from form input or falls back to `company_settings.address`.
   - Starts transaction: inserts into `appointments` and updates `applications.status = 'INTERVIEW_SCHEDULED'`.
   - Inserts into `application_status_history`.
   - Commits transaction.
4. Server dispatches `INTERVIEW_SCHEDULED` notification to candidate and confirmation to HR.
5. Candidate views updated interview details on `/candidate/interview`.

22.4 Batch Intern Allocation Flow
1. HR selects a batch project on `/hr/batch-allocation` -> `GET /api/hr/projects/[id]/batch-allocation`.
2. Server queries `getEligibleBatchCandidates()`: filters candidates with `applicant_type = 'BATCH_INTERN'` and `status = 'SELECTED'`.
3. Server builds Skill Heatmap by computing compatibility percentage for each candidate against each project module.
4. If no confirmed teams exist, server runs `generateAllocationDraft()`:
   - Calculates target number of squads.
   - Groups candidates by primary strength module.
   - Executes balanced snake round-robin to form squads.
   - Assigns distinct modules within each squad to maximize skill coverage.
   - Flags low-compatibility assignments (<60%) and uncovered module warnings.
5. HR reviews heatmap and draft teams in UI, makes any manual adjustments, and clicks "Confirm Allocation".
6. Client issues `POST /api/hr/projects/[id]/batch-allocation/confirm` with validated payload.
7. Server begins transaction: deletes old team records for this project, inserts new `teams`, inserts `team_members` mappings, dispatches in-app notifications (`BATCH_TEAM_ASSIGNED`) to all candidates, and commits transaction.
8. Candidates visit `/candidate/team` and immediately see their confirmed squad name, assigned project module, and teammate roster.

24. INPUT VALIDATION & DATA INTEGRITY SPECIFICATION
================================================================================

24.1 Name & Email Validation (`server/validation/auth.ts`)
- Name Constraints: Length between 2 and 100 characters; regex `/^[\p{L}\p{M}' ]+$/u`; rejects consecutive spaces; verifies apostrophes only appear between letters; rejects leading or trailing spaces.
- Email Constraints: Length <= 254 characters; single `@` symbol; local part <= 64 characters without consecutive dots; domain contains valid dot and extension of at least 2 alphabetic characters; rejects whitespace.

24.2 Password & OTP Validation
- Passwords must be at least 6 characters in length.
- OTPs must be exactly 6 numeric digits (`/^\d{6}$/`).
- Rate limiting: Max 5 failed attempts per OTP before permanent invalidation.

24.3 File Upload & Multipart Validation
- Resume Formats: Checked dynamically against `company_settings.allowed_formats` (defaults to `.pdf`, `.docx`, `.tex`).
- File Size Ceiling: Checked dynamically against `company_settings.max_file_size_mb` (defaults to 5 MB; system maximum 50 MB).
- Empty File Checks: Aborts if `file.size === 0` or extracted text length < 15 characters.
- Company Logo: Restricted to PNG, JPG, JPEG, WEBP, SVG; maximum 2 MB.

24.4 Project & Batch Allocation Payload Validation
- Target Team Size: Constrained between 2 and 20 (defaults to 4).
- Confirmed Teams Payload: Validates JSON object structure; ensures non-empty team arrays; validates positive integer user IDs, application IDs, and module IDs; enforces candidate uniqueness across all squads.

25. SECURITY ARCHITECTURE & THREAT MITIGATION
================================================================================

1. SQL Injection Mitigation:
   The system exclusively executes parameterized SQL statements through `mysql2` (`db.execute(sql, [params])` and `connection.execute(sql, [params])`). Raw user inputs are never concatenated directly into SQL query strings.

2. Cross-Site Scripting (XSS) Mitigation:
   All authentication credentials (JWTs) are transmitted in HTTP-only cookies (`httpOnly: true`). Client-side JavaScript running in the browser cannot read or exfiltrate the token. React automatically encodes dynamic variables rendered in TSX components, preventing DOM-based injection.

3. Cross-Site Request Forgery (CSRF) Mitigation:
   Cookies are configured with `sameSite: "lax"`, preventing third-party malicious websites from forging state-modifying POST/PUT requests on behalf of authenticated users.

4. Cryptographic Integrity:
   - User passwords hashed using bcrypt with salt factor 10.
   - Session tokens signed using HMAC-SHA256 with server-side secrets.
   - OTP codes and temporary reset authorization tokens are hashed using SHA-256 before storage in the database, preventing compromise even in the event of database exposure.

5. Information Disclosure & Enumeration Mitigation:
   Password recovery endpoints return identical generic responses whether an email address exists or not, preventing attackers from probing for registered user accounts.

6. Relational Integrity & Race Condition Mitigation:
   Critical multi-step mutations (application creation, batch allocation, status updates, job role approvals) are executed within database transactions using `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK`, and `SELECT ... FOR UPDATE` row-level locking where applicable.

The codebase implements comprehensive error handling across server routes and services:

29. CORE BUSINESS LOGIC RULES & SYSTEM INVARIANTS
================================================================================

1. Single HR Enterprise Invariant:
   The recruitment system is designed for a single administrative organization. Database queries locating HR credentials execute `WHERE role = 'HR' ORDER BY id ASC LIMIT 1`.

2. Category Segregation Invariant:
   Vacancies and applications are partitioned into three immutable categories: `SINGLE_JOB_SEEKER`, `SINGLE_INTERN`, and `BATCH_INTERN`. A candidate registered as a Job Seeker can only apply to Job Seeker vacancies.

3. Historical Applicant Type Preservation:
   When HR approves a candidate's request to change their applicant type (`approveJobChangeRequest`), the candidate's active type in `users.applicant_type` is updated, but previously submitted records in `applications.applicant_type` remain untouched, preserving historical audit integrity.

4. Duplicate Application Prevention:
   A candidate may only apply once to a given project vacancy (`SELECT id FROM applications WHERE user_id = ? AND project_id = ?`). Attempting to re-apply returns `409 Conflict`.

5. Application State Immutability:
   Decisions marked `SELECTED` or `REJECTED` are terminal. No further status modifications are permitted.

6. Interview-Decision Precedence Rule:
   HR cannot mark an application as `SELECTED` or `REJECTED` if an interview appointment is actively in `SCHEDULED` status. The interview must first be transitioned to `COMPLETED` or `CANCELLED`.

7. Minimum Resume Content Threshold:
   Ingested resumes must yield at least 15 characters of readable plaintext after sanitization; otherwise, the submission is rejected as unprocessable.

8. Batch Allocation Eligibility Constraint:
   Only candidates who applied as `BATCH_INTERN` and have reached `SELECTED` status can be included in squad allocation.

30. TECHNICALLY SIGNIFICANT INNOVATIONS & ARCHITECTURAL HIGHLIGHTS
================================================================================

1. In-Process Native Multi-Format Document Parsing:
   Eliminated the common architectural antipattern of deploying fragile, heavy Python microservices or subscribing to costly commercial OCR APIs. The system parses PDF, DOCX, and LaTeX source files entirely in-process using Node.js TypeScript libraries.

2. Deterministic Two-Stage Batch Allocation Heuristic:
   Developed a reproducible mathematical algorithm that balances team sizes, ensures primary skill distribution across squads via snake round-robin, and maximizes module-specific skill coverage, providing automated warnings for low-compatibility assignments (<60%) without AI hallucinations.

3. Live Single Source of Truth Keyword Analytics:
   Rather than storing static snapshots of matched keywords in text blobs, the API dynamically reconciles applicant resume text against active project keywords, calculating real-time breakdowns of earned scores, max scores, and weighted matched/missing lists.

4. ACID-Compliant Transaction Management:
   Critical business operations execute with strict transactional boundaries, ensuring that partial failures (such as a database disconnect after file storage) trigger automatic filesystem rollbacks and database rollbacks.

5. Cryptographic Multi-Stage Password Reset:
   Constructed a robust password recovery pipeline employing CSPRNG OTP generation, SHA-256 token hashing, strict brute-force rate-limiting (5 attempts max), 5-minute expirations, and single-use authorization tokens.

32. ARCHITECTURAL & IMPLEMENTATION EVOLUTION HISTORY
================================================================================

Based strictly on code comments, deprecated blocks, and active structural implementations, the following development evolutions occurred:

1. Relational Migration of Appointments:
   Early iterations stored mock interview data directly on application statuses. The project subsequently evolved to introduce the dedicated `appointments` table with distinct scheduling states (`SCHEDULED`, `COMPLETED`, `CANCELLED`), online meeting links, and physical address resolution. However, the HR dashboard endpoint (`app/api/hr/dashboard/route.ts`) still retains an un-migrated counter (`const upcomingInterviews = 0;`) referencing this transition.

2. Centralization of Enterprise Physical Location:
   Originally, offline interview addresses were resolved from individual HR profile fields (`users.company_address`). This was refactored in `server/services/interviewService.ts` to designate `company_settings.address` as the single source of truth for corporate venues, ensuring interview locations remain consistent regardless of HR personnel changes.

3. Refactoring of Application Listing Route:
   Initially, candidate application retrieval was drafted inside `app/api/applications/route.ts` as a GET handler. This was commented out and migrated to a dedicated, role-scoped route handler at `app/api/candidate/application/route.ts`.

4. In-Memory Extraction Migration:
   Project documentation notes indicate early planning for external Python-based NLP microservices. The final active implementation completely replaced this with native Node.js TypeScript extraction libraries (`pdf-parse`, `mammoth`, `Buffer`), resulting in a self-contained monolithic Next.js architecture.

33. TECHNICAL LIMITATIONS OF CURRENT IMPLEMENTATION
================================================================================

1. Substring Keyword Matching:
   The matching engine uses exact substring inclusion (`normalizedResume.includes(normalizedKeyword)`). It lacks morphological stemming (e.g., "managing" vs. "management") and semantic synonym awareness (e.g., recognizing that "PostgreSQL" satisfies "Relational Database").

2. Lack of Optical Character Recognition (OCR):
   Resumes submitted as flattened raster images or scanned PDFs without embedded text layers cannot be parsed and trigger an unprocessable entity error.

3. Single HR Profile Assumption:
   The repository and service logic use `ORDER BY id ASC LIMIT 1` when resolving the HR administrator, limiting multi-tenant corporate deployments where multiple HR recruiters have segregated project domains.

4. Local Filesystem Resume Storage:
   Resumes are stored on the local server disk (`process.cwd()/uploads/resumes/`). In ephemeral cloud container environments (such as AWS Lambda, Vercel Serverless, or Kubernetes pods), files stored locally will not persist across container recycling without mounted persistent volumes or S3-compatible cloud object storage.

5. Absence of Automated Test Suites:
   The codebase lacks automated regression, integration, or end-to-end test suites (e.g., Jest, Vitest, Playwright), relying instead on TypeScript compilation and manual QA.
